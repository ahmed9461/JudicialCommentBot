# الفهرس القضائي الرسمي — Official Judicial Catalog

## القرار المعماري

البحث عبر نموذج لغوي ليس بوابة إلزامية لاختيار القضية. المسار الأساسي للمشروع هو فهرس محلي دائم مبني من ملفات الأحكام والمدونات المنشورة لدى الجهات الرسمية. البحث عبر DeepSeek يبقى خياراً احتياطياً فقط عندما لا يوفر الفهرس عدداً كافياً من المرشحين ذوي الصلة المباشرة.

الهدف هو حل أربع مشكلات جوهرية:

1. عدم دفع تكلفة بحث ويب في كل طلب.
2. عدم الاعتماد على قدرة نموذج لغوي على اكتشاف رابط PDF رسمي مباشر في كل مرة.
3. ضمان أن المرشح يبدأ أصلاً من ملف رسمي معروف يمكن تنزيله والتحقق منه واستخراج صفحاته دون إعادة إنشاء المحتوى.
4. منع اختلاف منطق الفهرسة عن منطق التحقق وقت الطلب؛ القضية التي يدخلها الفهرس يجب أن تكون قابلة للتحقق لاحقاً بنفس القواعد.

## التدفق

Official source manifest -> Download official PDF -> Shared primary-header parser -> Exact physical case ranges + source SHA-256 -> Versioned local catalog -> Broad retrieval -> Strict course relevance gate -> Provenance verification -> Extract original pages -> Final boundary/identity validation -> Deduplication/ranking -> Commentary from verified text only -> DOCX

إذا أعاد الفهرس أقل من العدد المطلوب:

Verified local catalog -> bounded DeepSeek web fallback -> official PDF verification -> strict relevance gate on final judgment text -> merge -> ranking

## الثوابت المعمارية للفهرس

هذه القواعد عقود بين مرحلة الفهرسة ومرحلة التسليم:

- يوجد محلل واحد لرؤوس الأحكام في `app/pdf/headers.py` تستخدمه الفهرسة والتحقق وقت الطلب معاً.
- المحلل يفرق بين `primary judicial header` الذي يبدأ حكماً منشوراً وبين أرقام القضايا المذكورة داخل تسبيب حكم آخر.
- ذكر عبارة مثل `في القضية رقم ...` داخل متن الحكم لا ينشئ حد قضية جديداً.
- بداية الحكم تقبل عندما يظهر رقم القضية في منطقة البيانات الأولى مع دليل بنيوي قوي مثل `محكمة الدرجة الأولى` أو مجموعة كافية من حقول النشر الرسمية.
- لا يملك الـIndexer صيغة مستقلة لاستخراج رقم القضية تختلف عن Runtime verifier.
- صفوف الفهرس تحفظ الصفحات الفيزيائية الفعلية داخل PDF الرسمي، وليس رقم صفحة مطبوعاً أو رقماً من الكشاف.
- كل مجموعة مفهرسة مرتبطة ببصمة SHA-256 للملف الرسمي الذي بُنيت منه نطاقات القضايا.
- مرشح الفهرس يحمل `catalog_key` و`catalog_pdf_sha256` ونطاق الصفحات، ويعلّم بأنه `catalog_range_verified`.
- عند الطلب يعاد تنزيل الملف الرسمي، وتُقارن بصمته بالبصمة المفهرسة. إذا تغير الملف فلا تستخدم الصفحات القديمة ويطلب تحديث الفهرس.
- عند تطابق البصمة لا يعاد اكتشاف مكان القضية من الصفر؛ تستخرج الصفحات الموثقة مباشرة ثم يثبت Runtime أن أول صفحة هي رأس القضية نفسها وأنه لا يوجد رأس قضية أخرى داخل المقتطف.
- نطاقات صفحات آتية من بحث ويب أو مصدر غير مفهرس لا تعامل كموثقة؛ تبقى مجرد hints وتحتاج اكتشافاً وتحقيقاً وقت الطلب.

## جيل Parser ومنع البيانات القديمة

`CATALOG_PARSER_VERSION` يتغير كلما تغيرت قواعد اكتشاف رأس الحكم أو حدوده. الإصدار الحالي هو **4**. البحث والاستعلامات التشغيلية تعرض فقط الصفوف التابعة للجيل الحالي.

لذلك أثناء إعادة بناء جيل جديد:

- لا يعرض البوت سجلات من Parser قديم على أنها جاهزة.
- `/catalog` و`python -m app.catalog stats` يوضحان الجيل المتحقق الحالي.
- إذا لم يكتمل أي ملف من الجيل الحالي بعد، تكون الحالة `catalog_not_ready` بدلاً من استخدام بيانات قديمة أو اللجوء للويب لإخفاء المشكلة.
- إعادة فهرسة مجموعة تستبدل snapshot المجموعة ذرياً، حتى لو نتج عنها صفر قضايا؛ لا تبقى قضايا قديمة عالقة من Parser سابق.

## تغطية جميع المقررات

لا يوجد منطق خاص بمقرر واحد داخل كود الفهرس. جميع المقررات الـ34 تمر عبر نفس المحرك.

تخصيص كل مقرر يأتي من:

- `knowledge/subjects/<slug>.yaml`: الموضوعات، كلمات البحث، الأنماط المناسبة، الأنماط الضعيفة ومحاور التعليق.
- `config/subject_source_map.yaml`: الجهات الرسمية المفضلة لكل مقرر.

مرحلة الاسترجاع الأولية واسعة حتى لا تفوّت قضايا محتملة، لكن كل مرشح يمر بعد ذلك على `assess_subject_relevance` من `app/ranking/relevance.py`. هذه البوابة تعتمد على المفاهيم المميزة في ملف المادة وتتجاهل الكلمات القانونية العامة قدر الإمكان. ثم تعاد البوابة مرة أخرى على **النص النهائي المستخرج من PDF المتحقق**، لذلك لا يستطيع مرشح جاء من Web Search تجاوز شرط الصلة المباشرة.

الهدف هو منع ربط قضية خاصة بعيدة بمقرر مثل القانون الدستوري لمجرد احتوائها كلمات عامة من نوع: محكمة، حق، اختصاص أو نظام.

## مصادر الفهرسة

`config/catalog_sources.yaml` هو سجل المصادر القابلة للفهرسة. يدعم حالياً:

- مجموعات وزارة العدل الرسمية لعام 1434هـ.
- مجموعات وزارة العدل الرسمية لعام 1435هـ.
- مدونات ديوان المظالم عبر صفحة المدونات القضائية الرسمية.
- مدونات قرارات الأمانة العامة للجان الزكوية والضريبية والجمركية.
- صفحات القرارات والمبادئ الرسمية للجان الفصل في منازعات الأوراق المالية.
- اللجان التأمينية عبر صفحات القرارات الرسمية المسجلة في الـmanifest.

يمكن إضافة مصدر جديد من `source_registry.yaml` إلى manifest دون تغيير منطق الاختيار.

## قواعد قبول الحكم في الفهرس

الفهرس لا يقبل صفحة لمجرد وجود رقم فيها. القبول يتطلب رأساً قضائياً أولياً صريحاً يستطيع المحلل المشترك قراءته.

صفحات الكشاف التي تسرد أرقاماً كثيرة بلا رأس حكم لا تصبح قضايا. وفي المقابل، إذا ذكر حكمٌ قائماً قضية أخرى أو حكماً سابقاً داخل التسبيب، يبقى ذلك جزءاً من متن الحكم ولا يقسم النطاق. حد الحكم يمتد حتى بداية `primary judicial header` التالي فقط.

بعض ملفات PDF العربية تستخرج النص بترتيب بصري؛ المحلل المشترك يملك fallback محدوداً لعكس الأسطر فقط عندما يفشل الاستخراج المباشر كلياً، حتى لا تتحول المشكلة إلى أرقام معكوسة أو معرفات وهمية.

## قواعد الأصالة والتسليم

الفهرسة لا تجعل القضية معتمدة للتسليم تلقائياً. عند الطلب يمر المرشح على طبقة تحقق مستقلة تشمل:

- النطاق الرسمي والمسموح.
- HTTPS وتحويلات آمنة.
- Magic bytes وبنية PDF.
- مطابقة SHA-256 للمجموعة عند استخدام نطاق مفهرس.
- استخراج صفحات القضية مباشرة من الملف الرسمي دون إعادة رسم أو OCR أو إنشاء محتوى جديد.
- وجوب أن تبدأ أول صفحة في المقتطف برأس القضية الأساسية نفسها.
- رفض المقتطف إذا بدأ بذيل قضية سابقة أو احتوى رأس قضية تالية.
- اعتماد رقم القضية والبيانات التعريفية من الرأس الأولي الرسمي، لا من أرقام المعاملات أو الأحكام المشار إليها داخل المتن.
- بوابة صلة مباشرة بالمقرر على نص الحكم المتحقق نفسه.
- منع التكرار والحجز.

الفهرس لا ينشئ PDF ولا يعيد كتابة الحكم.

## عزل كتابة التعليق

DeepSeek لا يستلم وصف الاكتشاف أو `legal_issue` الذي كوّنه محرك البحث. إدخال كتابة التعليق يقتصر على:

- معرفة المقرر.
- البيانات التعريفية التي ثبتت بعد التحقق من PDF.
- نص الحكم النهائي المستخرج من المقتطف المتحقق.
- المصدر الرسمي.

وبذلك لا يمكن لوصف مرشح أو قضية مجاورة أن تنتقل إلى التعليق عبر قناة discovery metadata. كما يرفض Validator أي رقم قضية معلّم في التعليق يختلف عن رقم القضية المتحقق، إضافة إلى فحص أرقام المواد النظامية.

## بناء الفهرس

```bash
python -m app.catalog refresh
```

عرض حالة الجيل الحالي:

```bash
python -m app.catalog stats
```

فحص تغطية المقررات:

```bash
python -m app.catalog coverage
```

إعادة فهرسة الملفات الموجودة عمداً:

```bash
python -m app.catalog refresh --force
```

عند رفع `CATALOG_PARSER_VERSION` لا يلزم `--force`: الملفات ذات إصدار Parser أقدم تعاد فهرستها تلقائياً.

## دور DeepSeek

DeepSeek لا يُستخدم لبناء الفهرس الرسمي ولا لإثبات أصالة PDF أو تحديد حدود حكم مفهرس. دوره:

1. fallback محدود للاكتشاف عندما يكون الفهرس المتحقق موجوداً لكن تغطية المقرر قليلة.
2. التحليل القانوني وكتابة التعليق بعد التحقق البنيوي والموضوعي من الحكم.

بهذا يستخدم النموذج في الفهم الدلالي والصياغة، بينما تبقى الفهرسة والأصالة والهوية ونطاق الصفحات وبوابة الصلة قرارات حتمية قابلة للاختبار.
