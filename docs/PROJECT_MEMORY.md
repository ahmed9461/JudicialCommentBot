# ذاكرة مشروع JudicialCommentBot

هذه الوثيقة هي المرجع الثابت لقرارات المشروع. أي تعديل جوهري على السلوك يجب أن ينعكس هنا مع تحديث الاختبارات والوثائق ذات الصلة.

## الهدف

بوت تلجرام يساعد في تكليف التعليق على حكم قضائي لمقررات القانون عبر:

1. اختيار مقرر من أزرار البوت.
2. العثور على حكم سعودي مناسب للمقرر من مصدر رسمي.
3. التحقق من أصل PDF وهوية الحكم وحدوده قبل اعتماده.
4. منع إعادة استخدام القضية عالميًا.
5. تحليل الحكم نفسه فقط وإنشاء DOCX عربي أكاديمي.
6. إرسال PDF الحكم وDOCX التعليق عبر تلجرام.
7. حذف الملفات التشغيلية بعد النجاح مع الاحتفاظ ببيانات القضية وسجل الاستخدام.

## الثوابت المعتمدة

### الصلاحيات

- المالك هو المستخدم المسموح به افتراضيًا.
- يمكن للمالك إضافة أو حذف مستخدمين عبر Telegram ID.
- غير المصرح لهم لا يمكنهم تشغيل مسار البحث أو التوليد.
- Owner ID يأتي من البيئة ولا يزال هو المرجع الأعلى للصلاحيات.

### جميع المقررات

- يدعم المشروع جميع المقررات الـ34 من خلال ملفات مستقلة في `knowledge/subjects/`.
- لا يوجد منطق خاص بمقرر بعينه داخل محرك الفهرسة أو التحقق.
- اختلاف المقرر يأتي من ملف المعرفة وخريطة تفضيل المصادر `config/subject_source_map.yaml`.
- ملفات المعرفة تحتوي موضوعات الأولوية، كلمات البحث، الأنماط المناسبة والضعيفة ومحاور التعليق.

### اختيار القضية

- التقييم النهائي من 100، والافتراضي: صلة المقرر 40، وضوح المسألة 20، جودة التسبيب 15، قيمة التعليق 15، جودة المصدر/PDF 10.
- `AUTO_ACCEPT_SCORE` الافتراضي 90 وقابل للتعديل.
- إذا لم تتحقق ثقة الاعتماد التلقائي يعرض البوت أفضل المرشحين للاختيار.
- لا تدخل قضية مرحلة الاختيار النهائي قبل نجاح التحقق من PDF الرسمي **وبوابة الصلة المباشرة بالمقرر على نص الحكم المتحقق**.

### Catalog First

- المسار الأساسي هو `Official Judicial Catalog` محلي ودائم، وليس DeepSeek Web Search في كل طلب.
- الفهرس يبنى deterministic من المصادر الرسمية ولا يستخدم LLM.
- كل مجموعة تحفظ معها SHA-256، وكل قضية تحفظ نطاق الصفحات الفيزيائي الفعلي داخل المجموعة.
- `CATALOG_PARSER_VERSION` يحدد جيل قواعد الفهرسة؛ الجيل الحالي هو **4**.
- صفوف الأجيال القديمة لا تدخل البحث التشغيلي.
- بعد رفع إصدار Parser يعاد بناء المصادر تلقائيًا؛ لا يلزم `--force` لمجرد تغير الإصدار.
- عملية الفهرسة منفصلة عن خدمة Telegram ولها systemd service/timer مستقل.

### حدود الحكم — invariant أساسي

- يوجد Parser واحد في `app/pdf/headers.py` تستخدمه الفهرسة والتحقق وقت الطلب.
- يجب التمييز بين:
  - `primary judicial header`: رأس البيانات الذي يبدأ الحكم المنشور.
  - رقم قضية مذكور داخل الوقائع أو التسبيب أو الاستئناف كمرجع لقضية أخرى.
- رقم قضية داخل متن حكم **لا ينشئ حدًا جديدًا** ولا يصبح هوية الحكم.
- بداية الحكم تعتمد على رقم قضية في منطقة البيانات الأولى مع علامات بنيوية رسمية، وأقواها `محكمة الدرجة الأولى`.
- حد القضية ينتهي قبل `primary judicial header` التالي فقط.
- المقتطف النهائي يجب أن يبدأ في أول صفحة برأس القضية الأساسية نفسها.
- إذا سبق الرأسَ ذيلُ قضية سابقة أو ظهر رأس قضية أخرى في صفحات المقتطف، يرفض الملف ولا يرسل.

### قاعدة PDF الأصلية

- ممنوع إنشاء PDF للقضية من نص الحكم واعتباره ملف القضية.
- الأنواع المقبولة:
  - `official_pdf`: ملف الحكم الرسمي المباشر كما نشر.
  - `official_compilation_extract`: صفحات أصلية من مجموعة رسمية، منسوخة كصفحات PDF دون إعادة رسم أو إعادة كتابة.
- عند استخدام نطاق مفهرس: يعاد تنزيل الأصل الرسمي وتطابق SHA-256 مع بصمة المجموعة المفهرسة قبل استخدام الصفحات.
- إذا تغيرت البصمة، يرفض النطاق القديم ويستلزم تحديث الفهرس.
- Web-discovered page ranges ليست موثقة تلقائيًا؛ تعامل كـ hints وتحتاج اكتشافًا وتحقيقًا وقت الطلب.
- لا يوجد fallback يعيد بناء الحكم من HTML أو من مخرجات النموذج.
- OCR ليس مسارًا افتراضيًا؛ الأحكام التي لا يمكن التحقق من نصها تستبعد بدل اختراع محتوى.

### هوية الحكم والبيانات التعريفية

- رأس الحكم الرسمي بعد التحقق هو المرجع النهائي لرقم القضية والمحكمة والسنة وقرار الاستئناف إن وجد.
- لا يجوز اعتماد رقم معاملة أو صك أو قضية مشار إليها داخل المتن كرقم القضية الأساسية.
- القيم غير المنطقية في حقول المحكمة مثل كلمات السرد لا تقبل كـmetadata.
- إذا تعارضت بيانات الاكتشاف مع الرأس الرسمي، يفوز الرأس الرسمي.

### الصلة بالمقرر

- الاسترجاع الأولي يمكن أن يكون واسعًا حتى لا يفوّت القضايا المحتملة.
- قبل ظهور المرشح للمستخدم يطبق `assess_subject_relevance` على نص الحكم المخزن في الفهرس.
- بعد تنزيل/استخراج الحكم، تطبق نفس البوابة مرة ثانية على **النص النهائي المتحقق**.
- الكلمات القانونية العامة مثل محكمة، حق، اختصاص، نظام لا تكفي وحدها لإثبات الصلة بمقرر متخصص.
- يجب وجود مفاهيم مميزة من `search_keywords` أو مجموعة كافية من `priority_topics` للمقرر.
- Web Search fallback لا يستطيع تجاوز هذه البوابة.

### دور DeepSeek

- DeepSeek Web Search fallback محدود عندما يكون الفهرس الحالي جاهزًا لكن لا توجد مرشحات محلية كافية.
- DeepSeek لا يقرر أصالة PDF، ولا يحدد حدود حكم مفهرس، ولا يثبت هوية القضية.
- في كتابة التعليق لا يرسل إلى DeepSeek وصف الاكتشاف أو `candidate.legal_issue`.
- مدخل الكتابة يقتصر على معرفة المقرر + metadata المتحقق + نص الحكم النهائي المتحقق + المصدر الرسمي.
- الهدف منع انتقال وقائع قضية مجاورة أو وصف مرشح قديم إلى التعليق.

### منع التكرار والتزامن

- منع التكرار عالمي بين المواد والمستخدمين.
- يعتمد على رقم القضية + المحكمة، وكذلك بصمة PDF/المقتطف الرسمي.
- الرابط وحده ليس مفتاح منع التكرار.
- توجد حجوزات مؤقتة لمنع مستخدمين متزامنين من اعتماد القضية نفسها.

### أسلوب Word

- النماذج التي قدمها المستخدم مرجع للأسلوب فقط وليست مصدر نص.
- البنية الأساسية تتكيف مع المقرر، وتشمل عادة:
  1. تلخيص الوقائع وربطها بالمقرر.
  2. تحديد المسألة القانونية وصلتها بالمقرر.
  3. تحليل تسبيب المحكمة والنصوص/المبادئ التي استخدمتها فعلاً.
  4. التعليق وتبرير الرأي.
- DOCX عربي RTL، مهني ومركز، بلا حشو أو إشارات لأداة التوليد.

### الممنوعات والتحقق النهائي

- ممنوع Markdown والرموز الخاصة به في DOCX.
- ممنوع ذكر AI أو DeepSeek أو ChatGPT أو Telegram أو اسم البوت أو عبارات ميتا.
- ممنوع اختراع وقائع أو أرقام قضايا أو مواد نظامية أو نسبتها للمحكمة دون سند.
- أرقام المواد المذكورة في التعليق تقارن بنص الحكم المتحقق.
- إذا ذكر التعليق رقم قضية معلّمًا يختلف عن رقم القضية الأساسية المتحقق، يرفض التعليق.
- metadata المطلوب في Word يجب أن يطابق metadata المتحقق من PDF.

### الاحتفاظ بالملفات وحالات الفشل

- PDF وDOCX ملفات تشغيلية مؤقتة.
- بعد نجاح الإرسال وتسجيل الاستخدام تنظف بحسب إعدادات المشروع.
- إذا فشل التوليد/التحقق/الإرسال فلا تسجل القضية كمستخدمة.
- عند فشل مرحلة لاحقة يمكن الاحتفاظ بالقضية والـPDF المتحقق في الجلسة مؤقتًا لإعادة المحاولة دون إعادة البحث.
- `إعادة توليد التعليق` تستخدم نفس القضية ولا تعد استخدامًا جديدًا.
- `قضية أخرى` تنظف الجلسة والحجوزات وتبحث عن بديل غير مكرر.

### التشغيل والأمان

- الأسرار في `.env` غير المتتبع.
- تنزيل PDF مقيد بـHTTPS والنطاقات الرسمية المسجلة مع حماية SSRF وحدود الحجم والصفحات والتحويلات.
- أعمال `pypdf` الثقيلة خارج event loop ولها مهلة مرحلة مستقلة حتى لا تتجمد تحديثات تلجرام.
- السجلات إلى stdout/stderr وتدار عبر journald في systemd.
- SQLite هي القاعدة الحالية مع migrations ونسخ احتياطي.

## اختبارات Regression الإلزامية

أي تغيير في parser أو الحدود أو الصلة يجب أن يحافظ على اختبارات تمنع تكرار الأخطاء التالية:

- ذيل قضية سابقة يحتوي رقم قضية مرجعية قبل رأس الحكم المطلوب.
- حكم يذكر قضية أخرى في تسبيبه دون أن تنقسم القضية خطأً.
- مقتطف يحتوي القضية المطلوبة ثم بداية القضية التالية.
- قضية شراكة/سيارات خاصة لا تمر كقضية دستورية لمجرد كلمات قانونية عامة.
- قضية تتناول الحقوق والحريات/المشروعية مباشرة تمر للقانون الدستوري.
- تعليق يذكر رقم قضية أجنبية عن الحكم المتحقق يرفض.

## حالة المشروع

المشروع يعتمد Catalog First لجميع المقررات الـ34، مع Parser v4 قائم على رؤوس الأحكام الأولية، تحقق مزدوج من حدود وهوية المقتطف، وبوابة صلة مباشرة تعمل بعد الاسترجاع وبعد التحقق من PDF. DeepSeek معزول عن اكتشاف هوية الحكم ويستخدم للفهم والصياغة فقط بعد نجاح التحقق الحتمي.

بعد أي تحديث يرفع `CATALOG_PARSER_VERSION` يجب ترك:

```bash
python -m app.catalog refresh
```

حتى يبني الجيل الحالي، ثم فحص:

```bash
python -m app.catalog stats
python -m app.catalog coverage
```

لا تعتبر زيادة عدد القضايا هدفًا بحد ذاته؛ الأولوية لقضايا يمكن استخراجها والتحقق منها وتسليمها بلا خلط وبصلة مباشرة حقيقية بالمقرر.
